# 모아 칸반보드 — Supabase 저장 버전

## 변경 사항

- 카드의 조회·생성·수정·삭제 및 드래그 상태 변경을 Supabase 데이터베이스로 처리합니다.
- 공용 보드와 개인 보드를 선택할 수 있습니다. 기본 화면은 공용 보드입니다.
- 이메일·비밀번호 회원가입, 로그인, 로그아웃을 제공합니다.
- 개인 보드는 로그인 사용자 본인의 카드만 표시하며, 데이터베이스 RLS도 같은 접근 규칙을 적용합니다.
- 서버 변경 성공 후 화면에 반영합니다. 실패하면 입력 및 기존 카드 상태를 유지하고 오류를 표시합니다.
- 카드 데이터는 localStorage/sessionStorage에 저장하지 않습니다. 로그인 토큰만 sessionStorage에 보관합니다.
- 다른 사용자의 변경은 보드의 새로고침 버튼 또는 페이지 새로고침으로 조회합니다. 실시간 동기화는 포함하지 않습니다.

## 반드시 먼저 할 일: 테이블 및 보안 정책 생성

1. 제공하신 Supabase 프로젝트의 SQL Editor를 엽니다.
2. `supabase-schema.sql` 전체 내용을 새 쿼리에 붙여 넣고 실행합니다.
3. `public.tasks` 테이블 생성 및 RLS 활성화를 확인합니다.

이 SQL은 **기존 tasks 테이블이 없는 상태에서 최초 1회 실행**하도록 작성했습니다. 재실행하면 이미 존재한다는 오류가 발생하며 트랜잭션이 취소됩니다. 기존 테이블을 삭제하지 않습니다. 실패 후 같은 쿼리 탭을 재사용한다면 먼저 `ROLLBACK;`으로 열린 트랜잭션을 종료하세요.

이 작업물은 소스 코드 및 SQL 파일입니다. 실제 Supabase 프로젝트에 테이블을 생성하거나 Vercel 배포를 변경한 것은 아닙니다.

## Supabase 인증 설정

1. Authentication의 Providers 또는 Sign In 설정에서 Email 로그인을 활성화합니다.
2. URL Configuration의 Site URL에 실제 Vercel 운영 주소를 설정합니다.
3. Redirect URLs에도 사용하는 운영 주소 및 필요한 프리뷰 배포 주소를 허용합니다. 프리뷰 주소는 필요한 범위만 허용하세요.
4. 이메일 확인을 활성화했다면 가입 후 인증 메일의 링크를 누르고 사이트에서 로그인합니다. 인증 링크를 통한 자동 로그인은 구현하지 않았습니다.
5. 비밀번호는 이 화면에서 최소 8자로 제한합니다. 프로젝트에 더 강한 비밀번호 정책이 설정되어 있으면 그 정책도 충족해야 합니다.

로그인 정보는 현재 탭의 sessionStorage에만 보관합니다. 같은 탭 새로고침에서는 로그인 상태를 복원하며, 새 탭이나 브라우저를 다시 열었을 때는 재로그인이 필요할 수 있습니다. 액세스 토큰이 만료되기 전 API 요청에서 리프레시 토큰으로 갱신합니다. 저장소 접근이 차단된 브라우저에서는 현재 페이지 메모리에서만 로그인 상태를 유지합니다.

## Vercel 반영

배포 저장소에서 기존 파일을 아래 파일로 교체하거나 추가합니다.

```text
index.html
styles.css
app.js
config.js
.vercelignore
```

`index.html`, `styles.css`, `app.js`, `config.js`는 같은 폴더에 두세요. 이미 정적 사이트로 배포하고 있다면 기존 루트 구조를 유지하고 변경을 커밋한 뒤 재배포합니다. 새 프로젝트라면 Framework Preset은 Other를 선택하고 별도 빌드 명령 없이 이 폴더를 정적 사이트 루트로 지정합니다. Output Directory를 지정해야 한다면 `.`을 사용합니다.

`config.js`에는 전달받은 Supabase URL과 publishable 키가 설정되어 있습니다. 이 키는 브라우저 공개용이며, 실제 접근 통제는 RLS와 SQL 권한이 담당합니다. `service_role`, `sb_secret_…` 등 비밀 키는 프런트엔드 파일이나 Vercel 정적 환경 변수에 넣지 마세요. 이 정적 구성은 Vercel 환경 변수를 자동으로 읽지 않습니다.

`.vercelignore`는 SQL 및 설명 문서를 배포 대상에서 제외합니다. SQL은 Supabase에서 직접 실행해야 하며 Vercel에서 실행되지 않습니다.

## 권한과 운영 시 주의

| 사용자 | 공용 보드 | 개인 보드 |
| --- | --- | --- |
| 비로그인 | 모든 공용 카드 조회·생성·수정·삭제 | 접근 불가 |
| 로그인 | 모든 공용 카드 조회·생성·수정·삭제 | 본인 카드만 조회·생성·수정·삭제 |

공용 보드는 링크를 아는 방문자뿐 아니라 공개 API 주소와 키를 사용하는 누구나 변경할 수 있습니다. 로그인·관리자 승인·초대 방식으로 제한하는 보드가 아닙니다. 민감한 내용은 공용 보드에 입력하지 마세요. 악의적 삭제나 스팸을 막는 별도 서버 측 제한은 포함하지 않았습니다.

개인 보드 소유자와 보드 종류는 생성 후 클라이언트에서 변경하지 못하도록 열 단위 UPDATE 권한을 제한했습니다. 공개 API를 직접 호출하더라도 다른 사람의 개인 카드에 접근할 수 없도록 RLS가 검사합니다. Supabase 관리자 및 서버용 고권한 접근은 별개입니다.

기존 브라우저 localStorage의 `moa-kanban-v1` 데이터는 자동 업로드하거나 삭제하지 않습니다. 이번 버전에서 읽지 않으므로 기존 브라우저 카드가 새 보드에 자동으로 나타나지는 않습니다.

## 배포 후 확인

1. 비로그인 상태로 공용 보드에서 카드 생성·수정·삭제 및 드래그 이동을 확인합니다.
2. 다른 브라우저에서 공용 보드를 새로고침해 같은 데이터가 보이는지 확인합니다.
3. 계정 A와 B를 각각 가입·인증합니다. 개인 보드에서 만든 카드가 다른 계정에 보이지 않는지 확인합니다.
4. 로그인 전 개인 보드 생성이 차단되는지 확인합니다.
5. 계정 A의 개인 카드 ID로 계정 B의 REST 요청을 시도했을 때 조회 결과가 없고 수정·삭제가 되지 않는지 확인합니다.
6. 같은 계정으로 다른 브라우저에서 로그인하면 개인 카드가 복원되는지 확인합니다.
7. 네트워크를 끊은 뒤 저장 시 오류가 표시되고 저장되지 않은 카드가 성공처럼 추가되지 않는지 확인합니다.

## 검증 범위

JavaScript 구문 검사 및 모의 API 기반 CRUD·로그인·보드 전환·실패 처리 테스트를 통과했습니다. 실제 프로젝트의 SQL 실행, 인증 메일 발송, RLS 실행 결과 및 Vercel 브라우저 테스트는 수행하지 않았습니다. 실제 인증 설정과 데이터베이스 적용 후 위 항목을 확인해야 합니다.
